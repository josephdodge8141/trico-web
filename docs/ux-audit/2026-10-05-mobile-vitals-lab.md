# Mobile loading lab — 2026-10-05

I ran two fresh Chromium loads of each public route on the local Compose preview at 390 × 844, device scale 1, with simulated 150 ms network latency, 200,000 bytes/s downstream throughput, 100,000 bytes/s upstream throughput, and 4× CPU slowdown. Each run waited for the page H1 and another 1.6 seconds. `PerformanceObserver` recorded Largest Contentful Paint (LCP) and layout shifts; the browser performance entries supplied First Contentful Paint (FCP) and encoded JavaScript transfer. These are **local synthetic observations**, not field Core Web Vitals.

The LCP element was visible hero text on every route: the lead paragraph on five pages and the H1 on Storage. That narrows the next performance investigation to the render path rather than hero image compression. A Home resource trace showed the initial stylesheet ending near 0.50 s, the entry JavaScript near 0.81 s, the route module near 1.14 s, and a large shared schema/runtime chunk near 2.05 s; Home text LCP occurred near 2.68 s. No component or theme change is justified from two local runs.

A later three-run Home trace under the same mobile throttling narrowed the delay further. The 129 KB encoded shared chunk finished at 2.04–2.06 s. A 545–660 ms main-thread task began immediately after its arrival; the H1 appeared at 2.63–2.78 s and hero-text LCP at 2.68–2.88 s. A sampling CPU profile attributed 478 of 529 non-idle JavaScript samples to that chunk, with Zod parse/check functions at the top. The chunk is named `auth` by the build but also contains the public content schema runtime. This is evidence of a public render-path cost; it does not isolate the exact parse call or predict field LCP. The initial font resources do not explain the observed gap between chunk arrival and H1 insertion. Preserve schema validation and CMS safety when exploring a lighter public path, and compare the same throttled action before and after any change.

I tested one narrow hypothesis: delaying the generic `editableValueSchema` parse inside each shared entity boundary until its editor sheet opened. The edited frontend built successfully and ran on the same Compose preview. Three fresh Home loads then showed hero-text LCP at **2.78, 2.82, and 2.94 s**, with the same shared chunk ending near 2.04–2.08 s and a 554–703 ms task immediately afterward. The earlier three-run trace was **2.68, 2.76, and 2.88 s**. This small comparison did not show an improvement, so I reverted the boundary change and restored the preview from the source branch. The cost is more likely in loading or initializing the shared runtime or parsing the complete page than in that particular boundary parse; a targeted profile would still be needed before a larger architecture change.

I then moved the eager validation of all 195 registered seed entities into `@app/schemas/server`; browser pages still import the canonical definitions and validate received content. The shared browser chunk fell from **129,146 to 99,710 encoded bytes** (127.13 to 96.62 KB gzip in the build report), and fresh public routes now transfer 215–232 KB of JavaScript instead of 240–256 KB. Three Home loads on the rebuilt Compose preview measured **2.55, 2.69, and 2.72 s** LCP. This confirms a transfer reduction but is not enough to claim a paint improvement. The local seed job, `check:ci`, and the 49-scenario/429-step live browser behavior run passed after the split.

In an isolated container with that exact rebuilt frontend, I also tested preloading its real shared JavaScript chunk; a 200 response with JavaScript content type confirmed the target. Three baseline Home loads measured **2.57–2.61 s** LCP, and three with the preload measured **2.66–2.70 s** under the same throttling. The preload moved the chunk request earlier but did not improve LCP in this small trial, so it was not added. An earlier preload attempt pointed to a stale hashed filename and fetched the SPA fallback; those readings were discarded.

Before claiming a speed improvement, gather production traffic or repeat lab measurements under the same conditions around a specific change. A later [local interaction timing lab](./2026-10-06-interaction-lab.md) measured selected menu and tab actions, but neither these samples nor the loading measurements establish page-level or field Interaction to Next Paint. The observed CLS covers only initial loading without visitor interaction.
